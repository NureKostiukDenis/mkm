# Контекст

У рантаймі Java (JDK 21+) віртуальні потоки (Virtual Threads, Project Loom) виконуються за моделлю $M:N$, де множина легковажних потоків простору користувача мультиплексується диспетчером `ForkJoinPool` на фіксований пул потоків-носіїв ($N$ carrier platform threads, за замовчуванням $N = \text{кількість логічних ядер CPU}$). При виконанні блокуючого сокетного чи мережевого I/O рантайм зберігає стек віртуального потоку в купу (`Continuation.yield()`) і відмонтовує його (`unmount`), вивільняючи потік-носій для виконання інших задач.

Проте механізм відмонтування принципово не працює при переході в нативний код. Нативні стек-фрейми (C/C++ ABI) використовують фіксовані адреси пам'яті операційної системи, які JVM не може релокувати в купу. Як наслідок, віртуальний потік закріплюється за потоком-носієм (**carrier pinning**). Це виникає як при використанні класичного **JNI (Java Native Interface)**, так і нового **Panama FFM (Foreign Function & Memory API, JEP 454)**. Якщо кількість віртуальних потоків, які одночасно виконують нативний виклик або блокуються під час зворотного виклику з нативного коду в Java (native callback), досягає або перевищує розмір пулу носіїв ($M_{\text{native}} \ge N$), настає повне вичерпання пулу (**carrier starvation**). У цьому стані всі черги планувальника паралізуються, спричиняючи лавиноподібне зростання затримок (cascading latency collapse) для всіх непов'язаних віртуальних потоків у системі.

У JDK 24 специфікація **JEP 491** ліквідувала пінінг на моніторах об'єктів Java (`synchronized`), через що нативний бар'єр (JNI та FFM) залишився головним джерелом **залишкового пінінгу (residual pinning)** в сучасній архітектурі JVM.

**Суть наукового гепу:** У рецензованій науковій літературі відсутній контрольований, версійно-стратифікований експеримент, який би прямо порівняв JNI та FFM за умов дозованого насичення пулу носіїв (carrier-pool pressure), різної топології викликів (downcalls проти callbacks) та порівняв їхній овергед із контрольними групами (блокуючий файловий I/O, сокетний I/O, синтетичне засинання).

# Що відомо

1. **Базові межі масштабування віртуальних потоків:** Дослідження Pandita (2024, [[Src-7]]) зафіксувало зростання throughput на 60.79% та зниження затримки на 28.8% для I/O-bound задач у JDK 21, але показало повну відсутність виграшу для CPU-bound навантажень. Журнальний бенчмарк FCoral (ACM TACO 2026, [[Src-1]]) виявив аномально високу хвостову затримку P99 віртуальних потоків Java при файлових операціях порівняно з Go та Rust Tokio.
2. **Ліквідація моніторного пінінгу в JDK 24 (JEP 491):** Починаючи з JDK 24, блокування у блоках та методах `synchronized` більше не закріплює віртуальний потік за потоком-носієм ([[Src-11]]).
3. **Збереження нативного закріплення стеків:** Специфікація JEP 491 ([[Src-11]]), інженерна документація Quarkus та галузевий аналіз InfoQ (2026) офіційно підтверджують, що нативні фрейми стеків та нативні callbacks залишаються джерелом непереборного закріплення носіїв у JDK 24/25.
4. **Методологічна невалідність наївних мікробенчмарків:** Schiavio et al. (ACM SAC 2026, [[Src-2]]) довели, що ізольовані JMH-бенчмарки викликів нативного коду на JVM спотворюються JIT-профілюванням і не відтворюють поведінки системи під конкурентним навантаженням; Di Grazia & Pradel (ACM OOPSLA 2026, [[Src-4]]) показали, що JVM не досягає стаціонарного стану через фонову деоптимізацію та троттлінг, вимагаючи непараметричного аналізу часових рядів замість середнього арифметичного.

# Що невідомо

1. **Відмінність ціни утримання носіїв між JNI та FFM:** Чи відрізняється поведінка планувальника `ForkJoinPool` при виконанні нативного блокування через прямий виклик Panama FFM (`Linker.downcallHandle()`) від класичного JNI-переходу при однакових інтервалах блокування нативного коду ($10\,\mu\text{s} \text{ – } 10\,\text{ms}$) та ідентичній користі коду на C/C++.
2. **Топологічний овергед зворотних викликів (Native-to-Java Callbacks):** Наскільки зростає ймовірність деградації пулу носіїв, коли нативний код здійснює зворотний виклик у Java, де віртуальний потік намагається заблокуватися (на сокеті чи лоці), і чи відрізняється стійкість JNI upcall від Panama FFM `MemorySegment` upcall stub.
3. **Критичний поріг фазового колапсу (Breakdown Threshold):** За якого співвідношення частоти нативних звернень, тривалості нативного блокування та кількості віртуальних потоків на один потік-носій ($M / N$) настає перехід від нормального виконання до колапсу хвостової затримки (P99/P99.9 latency explosion).
4. **Контраст зі стандартними блокуваннями рантайму:** Наскільки деградація системи при нативному пінінгу глибша за деградацію при звичайному блокуючому файловому I/O (який у Linux також може закріплювати носій), сокетному I/O та паркуванні (`LockSupport.park()`).
5. **Міжверсійний ефект (pre- vs post-JEP 491):** Як поводиться система в JDK 21 порівняно з JDK 25 у змішаних сценаріях, де нативний виклик сусідить із внутрішньою синхронізацією коду на Java.

# Чому важливо

* **Архітектурна надійність Enterprise-бекендів:** Сучасні Java-фреймворки (Spring Boot 3, Quarkus) та бібліотеки високої продуктивності масово інтегрують нативний C/C++ код: бібліотеки інференсу AI/ML (ONNX Runtime, TensorFlow C API), вбудовані сховища (RocksDB, LMDB), криптографію та нативні мережеві драйвери (Netty tcnative, epoll/io_uring). Раптове голодування carrier-пулу через нативний виклик паралізує черги всіх незалежних веб-запитів сервісу.
* **Обґрунтованість міграції з JNI на Project Panama FFM:** Спільнота просуває FFM як сучасну альтернативу JNI. Проте без експериментальних замірів поведінки черг планувальника невідомо, чи зменшує FFM навантаження на carrier-пул при високому паралелізмі, чи володіє тими самими вразливостями до carrier starvation.
* **Чистота наукових моделей продуктивності:** Поточні наукові публікації змішують усі типи затримок у загальну категорію «I/O-bound», маскуючи фундаментальну різницю між неблокуючим сокетним I/O (де потік відмонтовується) та нативним блокуванням (де потік закріплюється).

# Доказ 1

**Агрегація навантажень та відсутність ізоляції нативного переходу в існуючих бенчмарках ([[Src-7]], [[Src-8]], [[Src-1]]):**
* Робота Pandita (2024, [[Src-7]]) аналізує узагальнені макронавантаження «I/O-intensive» та «CPU-intensive», не виділяючи роботу з нативними викликами JNI/FFM та не фіксуючи черги carrier-пулу.
* Дослідження Likus & Kruzel (ECMS 2025, [[Src-8]]) аналізує віртуальні потоки в Spring Boot, де падіння пропускної здатності виникає через ліміти з'єднань пулу HikariCP та сокетів ОС, що маскує внутрішні процеси у планувальнику JVM.
* Фреймворк FCoral (ACM TACO 2026, [[Src-1]]) тестує рантайм Java як «чорну скриньку» за допомогою формальних високорівневих задач (CWP), але не проводить цільового дослідження нативного бар'єру JNI/FFM під тиском пулу носіїв.

# Доказ 2

**Офіційне визнання проблеми залишкового пінінгу в інженерних джерелах за відсутності кількісних академічних досліджень ([[Src-11]], документація Quarkus, InfoQ):**
* У тексті JEP 491 ([[Src-11]]) розробники OpenJDK прямо фіксують: розмонтування віртуальних потоків за наявності нативних стек-фреймів (C-frames) залишається нерозв'язаною проблемою архітектури JVM, через що JNI та FFM downcalls продовжують закріплювати носій.
* Інженерні настанови Quarkus та аналітичні звіти InfoQ (2026) виділяють блокуючі callbacks із нативного середовища в Java як критичну загрозу стабільності сервісів, проте не містять жодних систематичних вимірів хвостових затримок чи глибини черг носіїв.

# Яке дослідження може закрити gap

Для закриття гепу необхідний **версійно-стратифікований каузальний бенчмарк** із фіксованими системними бюджетами:

1. **Факторна матриця порівняння:**
   * **Версія JVM:** OpenJDK 21 LTS (базова версія з моніторним пінінгом) проти OpenJDK 25 LTS (post-JEP 491, де залишається лише нативний пінінг).
   * **Механізм нативного виклику:** Класичний JNI проти Panama FFM (`java.lang.foreign`, JEP 454) з ідентичною нативною C-бібліотекою.
   * **Топологія виклику:**
     1. *Direct Downcall:* Java $\rightarrow$ Native blocking ($t_{\text{sleep}}$ на рівні C/POSIX nanosleep).
     2. *Blocking Callback:* Java $\rightarrow$ Native $\rightarrow$ Java callback (з блокуванням усередині Java на сокеті чи лоці).
   * **Контрольні базисні групи:** Блокуючий сокетний I/O (відмонтування працює), блокуючий файловий I/O (перевірка поведінки epoll/io_uring), синтетичне засинання (`LockSupport.parkNanos`).
   * **Фактори тиску навантаження:** Розмір пулу носіїв ($N \in \{2, 4, 8\}$ потоків через `-Djdk.virtualThreadScheduler.parallelism`), рівень конкурентності ($M \in [1..500] \times N$ віртуальних потоків), тривалість нативного блокування ($t_{\text{block}} \in [10\,\mu\text{s}, 100\,\mu\text{s}, 1\,\text{ms}, 10\,\text{ms}]$).
2. **Цільові метрики:**
   * *Продуктивність та хвостова затримка:* Throughput (RPS/ops), розподіл затримок (P50, P90, P99, P99.9, Max latency cliff).
   * *Телеметрія рантайму JVM:* Частота та сумарний час подій `jdk.VirtualThreadPinned` (JFR), середня та пікова черга `ForkJoinPool` (`getQueuedTaskCount`), активні carrier-потоки.
   * *Системні метрики ядра ОС:* Кількість перемикань контексту (`voluntary` та `involuntary context switches` через `/proc/[pid]/status`), використання CPU в режимі kernel/user.
3. **Методологічні запобіжники:**
   * Ізоляція ядер CPU (`taskset` / isolcpus);
   * Вимкнення механізмів динамічного розгону частоти CPU (Intel Turbo Boost / AMD Core Performance Boost);
   * Статистичний аналіз сегментів сталих вимірів без усереднення за нестаціонарні прогрівочні періоди (відповідно до рекомендацій [[Src-4]]).

# Що спростує gap

1. Публікація рецензованого дослідження, в якому вже реалізовано факторіальне порівняння JNI та FFM за умов контрольованого тиску на пул носіїв із реєстрацією глибини черги carrier threads та латентності P99/P99.9.
2. Емпіричний доказ того, що різниця у вартості переходу між JNI та FFM є зневажливо малою порівняно зі звичайною дисперсією I/O, а нативне блокування не призводить до додаткової деградації черги планувальника порівняно зі стандартним файловим блокуванням.
3. Випуск оновлення JVM, яке реалізує апаратне або компіляторне розмонтування нативних C-фреймів стеків (native stack unmounting / segmented stacks), що повністю зніме проблему залишкового пінінгу в нативному коді.
