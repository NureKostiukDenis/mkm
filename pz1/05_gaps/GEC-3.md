Title: Експериментальна невизначеність поведінки нативного бар'єру FFM/JNI у віртуальних потоках Java під навантаженням carrier-пулу

# Контекст

З випуском Project Loom у Java (JDK 21+) концепція багатопотоковості зазнала кардинальної трансформації: замість традиційних важких платформених потоків ОС розробники отримали легковажні віртуальні потоки (Virtual Threads). Віртуальні потоки виконуються в просторі користувача та мультиплексуються планувальником JVM (`ForkJoinPool`) на невеликий фіксований пул потоків-носіїв (carrier threads), кількість яких за замовчуванням дорівнює числу доступних логічних ядер процесора.

Основне призначення віртуальних потоків — масштабування операцій вводу-виводу (I/O-bound). Коли віртуальний потік виконує блокуючий сокетний або мережевий I/O, JVM автоматично відмонтовує (unmount) його від потоку-носія, дозволяючи носію виконувати інші віртуальні потоки. Однак, якщо віртуальний потік переходить у нативний код (через класичний Java Native Interface — JNI, або сучасний Foreign Function & Memory API — Project Panama / FFM), відмонтування стає неможливим через прив'язку стек-фреймів до пам'яті ОС. Це явище відоме як закріплення носія (**carrier pinning**). Якщо велика кількість віртуальних потоків одночасно викликає нативний код або блокується під час нативних зворотних викликів (native callbacks), пул носіїв виснажується (**carrier starvation**), що здатне паралізувати всю багатопотокову систему.

У JDK 24 специфікація **JEP 491** ліквідувала пінінг на синхронізаторах рівня Java (`synchronized` блоки та методи), перевівши проблему пінінгу в розряд виключно **залишкового пінінгу (residual pinning)** на межі взаємодії з нативним кодом (JNI та FFM).

---

# Що відомо

1. **Ефективність VT на макрорівні:** Віртуальні потоки забезпечують зростання пропускної здатності на 60–140% та зниження затримок P99 для простих мережевих I/O операцій, але не дають виграшу для CPU-bound навантажень і можуть демонструвати нестабільні хвостові затримки при файловому копіюванні ([[Src-7]], [[Src-1]]).
2. **Усунення моніторного пінінгу:** Починаючи з JDK 24, завдяки JEP 491, блокування на моніторах об'єктів Java більше не закріплює віртуальний потік за потоком-носієм ([[Src-11]]).
3. **Незмінність нативного пінінгу:** Нативні стекові кадри (як JNI, так і FFM downcalls), а також виклики з нативного коду назад у блокуючий Java-код (native-to-Java callbacks) фундаментально утримують або блокують потоки-носії в усіх версіях JVM, включаючи JDK 24/25 ([[Src-11]], документація Quarkus, InfoQ).
4. **Методологічні пастки JVM:** Наївні мікробенчмарки JMH для ізольованого виклику JNI чи FFM спотворюються профілем JIT-оптимізатора і не відтворюють поведінки за реальної конкуренції ([[Src-2]]), а сучасні JVM не досягають стаціонарного стану, вимагаючи непараметричного аналізу часових рядів замість середнього арифметичного ([[Src-4]]).

---

# Що невідомо

1. **Порівняльна ціна JNI проти FFM:** Чи відрізняється вартість утримання пулу carrier threads між новим Panama FFM API та класичним JNI при еквівалентній нативній роботі та однакових інтервалах блокування за умов високого паралелізму.
2. **Вплив топології виклику (Callbacks):** Наскільки сильніше блокуючі зворотні виклики (Java $\rightarrow$ Native $\rightarrow$ Java blocking callback) виснажують пул носіїв порівняно з прямими нативними викликами (downcalls), і чи є FFM більш стійким до цієї топології, ніж JNI.
3. **Пороги деградації (Phase Transition):** При якому рівні конкурентності (concurrency relative to carrier count) та якій тривалості нативного блокування ($10\,\mu\text{s}$ проти $10\,\text{ms}$) навантаження нативним кодом призводить до лавиноподібного вичерпання пулу носіїв і деградації P99/P99.9 латентності.
4. **Контраст із системними контролями:** Як деградація від нативного бар'єру співвідноситься з контрольними сценаріями: блокуючим файловим I/O, блокуючим сокетним I/O та синтетичним засинанням (`Thread.sleep` / `LockSupport.park`).
5. **Версійна динаміка (pre- vs post-JEP 491):** Як зміна механізму синхронізації у JDK 24 вплинула на стійкість до carrier starvation у змішаних сценаріях, де нативний код сусідить із внутрішньою синхронізацією.

---

# Чому важливо

* **Надійність Enterprise-систем:** Сучасні високонавантажені сервіси (Spring Boot, Quarkus) одночасно переходять на віртуальні потоки та використовують нативні бібліотеки (TensorFlow, PyTorch/ONNX Runtime, RocksDB, Netty tcnative, криптографічні модулі, драйвери БД). Виникнення carrier starvation на вузькому пулі носіїв (4–16 ядер) блокує виконання десятків тисяч непов'язаних веб-запитів, спричиняючи прихований системний збій (liveness failure та cascading latency explosion).
* **Технологічна міграція на Panama FFM:** Індустрія позиціонує FFM API як сучасну та безпечну заміну JNI. Без експериментальних даних розробники не можуть оцінити, чи FFM захищає від виснаження планувальника, чи створює аналогічні ризики.
* **Наукова чистота порівняльних досліджень:** Наразі в науковій літературі всі види затримок агрегуються в «I/O-bound», що маскує справжні архітектурні ботлнеки JVM.

# Доказ 1

**Агрегація навантажень та відсутність ізоляції нативного бар'єру в існуючих емпіричних дослідженнях віртуальних потоків ([[Src-7]], [[Src-8]], [[Src-1]]):**
* У роботі Pandita (2024, [[Src-7]]) порівняння platform vs virtual threads проводиться суто на макрокатегоріях («I/O» та «CPU»), без виокремлення JNI/FFM чи стану carrier pool.
* У дослідженні Likus & Kruzel (ECMS 2025, [[Src-8]]) падіння продуктивності за високої конкурентності виникає через вичерпання пулу сокетів та пулу з'єднань HikariCP, що маскує внутрішні планувальні ефекти JVM.
* Новітній фреймворк FCoral (ACM TACO 2026, [[Src-1]]) вимірює P99 затримку та пропускну здатність Java VT, але розглядає JVM як «чорну скриньку» на базі узагальнених завдань і не містить ізольованих експериментів із нативними викликами під тиском пулу носіїв.

# Доказ 2

**Архітектурна асиметрія та збереження ризику залишкового пінінгу в інженерних специфікаціях ([[Src-11]], Quarkus Guide, InfoQ 2026):**
* Офіційний документ JEP 491 ([[Src-11]]) прямо констатує, що розмонтування віртуальних потоків на нативних стек-фреймах не підтримується і залишається джерелом пінінгу в JDK 24+.
* Інженерні настанови Quarkus та галузевий аналіз InfoQ (2026) виділяють блокуючі callbacks із нативного середовища в Java як критичну загрозу голодування планувальника, але не надають жодних систематичних кількісних оцінок овергеду чи метрик хвостової затримки під навантаженням.

# Доказ 3

**Відсутність каузального порівняння в рецензованій методологічній літературі 2025–2026 років ([[Src-2]], [[Src-3]], [[Src-4]], [[Src-5]], [[Src-6]]):**
* Жодна з останніх робіт у провідних виданнях (ACM SAC '26, TOSEM '26, OOPSLA '26, ASPLOS '25) не проводить цільового експерименту щодо переходу JNI/FFM під тиском carrier pool.
* Натомість ці праці встановлюють строгі методологічні обмеження: мікробенчмарки JMH оманливі через JIT-профілювання ([[Src-2]]); для усунення шуму потрібна афінність процесора ([[Src-3]]); порівняння середніх арифметичних є невалідним через нестаціонарність рантайму ([[Src-4]]); а платформи типу Fray ([[Src-6]]) шукають дедлоки, а не міряють затримки утримання носіїв.

# Яке дослідження може закрити gap

Для закриття цього гепу необхідне магістерське або наукове дослідження, спроєктоване як **версійно-стратифікований каузальний бенчмарк** (factorial causal benchmark) із фіксованими ресурсними бюджетами:

1. **Фактори порівняння:**
   * **Версії JVM:** JDK 21 (до JEP 491, присутній моніторний пінінг) проти JDK 24/25 (post-JEP 491, лише залишковий нативний пінінг).
   * **Нативний механізм:** JNI проти Panama/FFM з ідентичною реалізацією C-бібліотеки.
   * **Топологія виклику:** Прямий виклик (downcall) проти зворотного блокуючого виклику (callback: Java $\rightarrow$ Native $\rightarrow$ Java).
   * **Контрольні групи:** Блокуючий файловий I/O, блокуючий сокетний I/O, синтетичне блокування (`LockSupport.park` / `Thread.sleep`).
   * **Тиск навантаження:** Рівень паралелізму carrier pool ($P \in \{2, 4, 8\}$), кратність конкурентності ($N \in [1..1000] \times P$), тривалість блокування ($t \in [10\,\mu\text{s} .. 100\,\text{ms}]$).
2. **Метрики:** Throughput (ops/sec), хвостова затримка (P90, P99, P99.9), реальна утилізація та черга планувальника (телеметрія JFR: `jdk.VirtualThreadPinned`, ForkJoinPool queue depth, active carrier count), процесорні цикли та перемикання контексту ОС.
3. **Методологічні запобіжники:** Фіксація ядер CPU (CPU affinity), вимкнення Hyper-Threading та динамічного розгону частоти, незалежні JVM-форки, сегментно-інтервальний статистичний аналіз часових рядів.

---

# Що спростує gap

1. Публікація рецензованого дослідження, в якому вже проведено факторіальне порівняння JNI та FFM за умов контрольованого тиску на пул носіїв із вимірюванням черги carrier threads та хвостових затримок.
2. Емпіричний доказ того, що накладні витрати нативного блокування в JNI та FFM статистично не відрізняються від звичайного файлового або сокетного блокування за будь-якої частоти викликів та тривалості, тобто нативний бар'єр не створює жодного специфічного овергеду на carrier pool.
3. Оновлення JVM, яке реалізує повноцінне відмонтування потоків-носіїв навіть за наявності нативних фреймів на стеку (native stack unmounting), що ліквідує залишковий пінінг на системному рівні.
